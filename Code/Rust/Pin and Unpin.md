# Pin and Unpin

Guaranteeing that values won't move in memory — required for self-referential structs and async.

## Why Moving Is Normally Fine

In Rust, values can always be moved (memcpy'd to a new address). The borrow checker ensures no references to the old location survive. This is fine for almost everything:

```rust
let x = 5;
let y = x;  // x moved to y — totally safe, x is an integer
```

## The Problem: Self-Referential Structs

A self-referential struct holds a pointer to one of its own fields. If the struct moves, the pointer becomes a dangling reference to the old address.

```rust
struct SelfRef {
    value: String,
    pointer: *const String,  // points to `value` above
}
```

If `SelfRef` moves in memory, `pointer` still points to the old address. This is undefined behavior.

Async state machines generated by `async fn` are self-referential — they store references to local variables that persist across `.await` points. This is why async needs `Pin`.

## What Pin Does

`Pin<P>` wraps a pointer type (like `Box`, `&mut`) and prevents the value behind it from being moved.

```rust
use std::pin::Pin;

let mut val = 5i32;
let pinned: Pin<&mut i32> = Pin::new(&mut val);
// You cannot move val while pinned exists
```

Once pinned, you can't get a `&mut T` out of it (which would allow moving via `std::mem::swap`). You can only get `Pin<&mut T>`.

## What Unpin Means

`Unpin` is a marker trait meaning "it's safe to move this type even after pinning."

Most types are `Unpin` — `i32`, `String`, `Vec<T>`, etc. For these, `Pin` is essentially a no-op; you can freely move them. Pinning only has real effect on `!Unpin` types (types that are NOT `Unpin`).

```rust
// These are Unpin — Pin<Box<i32>> lets you move the i32 anyway
let x: Pin<Box<i32>> = Box::pin(5);

// Futures generated from async fn are !Unpin — pinning actually matters
```

## Futures Must Be Pinned to Be Polled

The `Future` trait's `poll` method requires `Pin<&mut Self>`:

```rust
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```

This means before you can poll (drive) a future, you must pin it. The `.await` syntax does this for you automatically. When you call `future.await`, the compiler:
1. Pins the future on the stack
2. Polls it in a loop until it returns `Poll::Ready`

You only deal with `Pin` manually when implementing `Future` yourself or building executor/runtime code.

## Box::pin

The most common way to create a pinned value on the heap:

```rust
use std::pin::Pin;

// Pin a future on the heap
let fut: Pin<Box<dyn Future<Output = i32>>> = Box::pin(async { 42 });

// Equivalent
let fut = Box::pin(async { 42 });
```

`Box::pin` is commonly used when:
- You need to store a future in a struct field
- You need to erase the concrete future type with `dyn Future`
- You're building a collection of futures with different types

## pin! Macro (Stack Pinning)

`std::pin::pin!` pins a value on the stack without heap allocation:

```rust
use std::pin::pin;

let fut = async { 42 };
let mut pinned = pin!(fut);
// Now you can poll `pinned`
```

Used in hand-rolled executors and when you need to avoid allocation.

## Where You'll See This in Async Docs

### tokio::select! internals

`select!` pins each future branch before polling them.

### Storing futures in structs

```rust
struct MyStruct {
    fut: Pin<Box<dyn Future<Output = i32> + Send>>,
}

impl MyStruct {
    fn new() -> Self {
        Self {
            fut: Box::pin(async { expensive_work().await }),
        }
    }
}
```

### Async trait return types

Before Rust 1.75, async traits used `Box::pin` explicitly:

```rust
// Old pattern (before native async fn in traits)
fn fetch(&self) -> Pin<Box<dyn Future<Output = String> + '_>> {
    Box::pin(async move { /* ... */ })
}
```

Now native async fn in traits works directly in stable Rust.

### Unpin bounds in generics

You'll see `T: Unpin` in bounds when a generic function needs to move `T` after it might have been pinned:

```rust
fn use_future<F: Future + Unpin>(mut f: F) {
    // Can move f because it's Unpin
}
```

## PhantomPinned — Opting Out of Unpin

To make a type `!Unpin` (i.e., actually prevent moving after pinning):

```rust
use std::marker::PhantomPinned;

struct SelfRef {
    value: String,
    pointer: *const String,
    _pin: PhantomPinned,  // makes SelfRef !Unpin
}
```

`PhantomPinned` is a zero-sized type that removes the automatic `Unpin` impl.

## Mental Model

| | Unpin type (most types) | !Unpin type (async state machines) |
|---|---|---|
| `Pin<P>` effect | No effect, can still move | Truly prevents moving |
| Can get `&mut T` | Yes, via `Pin::get_mut` | No |
| Examples | `i32`, `String`, `Vec` | `async fn` futures |

## Tips

- In normal async code you never write `Pin` directly — `.await` handles it
- Reach for `Box::pin(async { ... })` when you need to store a future in a struct
- `Pin<Box<dyn Future<Output = T>>>` is the idiomatic "type-erased future" type
- `!Unpin` is not a trait you implement — it's the absence of `Unpin`
- If a compiler error mentions `Unpin`, you likely need `Box::pin` or the `pin!` macro
